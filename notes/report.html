PICO NEO 2 EYE A7B10 / PICOA7B10 SDM845 FEASIBILITY REPORT

Putting an open OS on the Neo 2

Findings from a static teardown of the PUI 4.1.3 firmware and an EDL firehose dump. The headline: the hard part is not the part that looked hard.

Verdict

More feasible than it first appeared, but the ceiling is set by Android 8.1, not by the VR stack. Pico's compositor turns out to be cleanly portable, the tracking hardware is standard parts with mainline Linux drivers, and the factory calibration is in an open, documented format. The genuine obstacle is that this device shipped on VNDK 27 with no published kernel source, which caps how far a blob-reuse port can travel.

There are two coherent routes. Reusing the stock vendor partition gets you a working headset quickly but pins you near Android 11. Going fully open with a mainline kernel, Mesa and Monado reaches a modern Android and satisfies the open-source goal, but it is a months-long project whose risk is concentrated in camera and display bring-up.

One caveat lands directly on the make-or-break requirement: the controllers are tracked electromagnetically, through an FPGA and signed DSP firmware. There is no open replacement for that and there will not be one. A fully-open build either carries those blobs or ships without controller tracking — worth deciding early, because it is the one place the goal cannot be fully met.

02 — The decisive test

Pico's compositor is portable

The question that gates everything is what the VR runtime links against. A compositor that reaches into libgui, libui or SurfaceFlinger internals is welded to the exact system image it shipped on, and dies on every Android version bump. One that stays inside the NDK travels freely.

libcompositor.pxr.so was built with NDK r20b against API 26, and its complete dependency set is liblog, libandroid, libEGL, libGLESv3, libvulkan, libdl, libc, libm. Every one is NDK-stable. The only framework surfaces it imports are ANativeWindow_fromSurface and standard EGL calls, both public NDK API.

ComponentLinks againstPortable?
libcompositor.pxr.so NDK-stable only Yes
qvrservice libqvrservice.so + NDK Yes
libconfigurationclient.pxr.so libbinder (no C++ symbols seen) Likely
libCVControllerClient.pxr.so android::Parcel, android::IBinder Rebuild glue
pvrservice libgui, libui, libbinder, libsensor, libpowermanager Version-bound

So the port cost is concentrated in pvrservice and the binder client libraries, which are the thin framework-facing glue rather than the graphics engine. That is a much smaller job than reimplementing a compositor, and it means keeping the closed runtime for backwards compatibility is a realistic goal.

03 — Two useful surprises

vrflinger and the calibration format

The display path is AOSP, not proprietary. surfaceflinger.rc opens pdx/system/vr/display/{client,manager,vsync} sockets, which is AOSP's vrflinger (frameworks/native/services/vr/). The direct-mode display service is open-source code you can build, not a blob you have to smuggle forward.

The factory calibration is a standard visual-inertial calibration. /persist/pvr/camera/device_calibration.xml is plain XML carrying FISHEYE_4_PARAMETERS (Kannala-Brandt) intrinsics, stereo rig extrinsics on a 79.5 mm baseline, IMU-to-camera transform (ombc/tbc), accelerometer and gyro biases, and a time offset. That is exactly the model Basalt, Kalibr and Monado consume.

Taken together these remove the two risks I would normally call project-killing: that direct-mode rendering is unportable, and that per-unit tracking calibration is locked in an opaque vendor format.

04 — Device tree

It's a Qualcomm reference design

The bootloader identifies the unit as QC_REFERENCE_PHONE, and every one of the 40 DTBO entries carries a stock Qualcomm model string — MTP, CDP, QRD, HDK, and notably SVR and QVR, Qualcomm's VR reference boards. Pico never renamed them.

So the device tree base is Qualcomm's public CAF sdm845 reference rather than a bespoke tree that would have to be reconstructed from scratch. The Pico-specific delta arrives as overlay fragments, and it is small enough to enumerate completely:

05 — QVR protocol

The VR service is sockets, not binder

libqvrservice_client.so exports 191 functions, and their signatures give the architecture away: QVRSocket, QVRSocketPkt_t, sockaddr_un, InitSharedMemAt, qvr_ring_buf_id, qvrservice_ring_buffer_desc_t, alongside a string-keyed GetParam/SetParam pair and StartVRMode/StopVRMode.

That is a Unix domain socket protocol with shared-memory ring buffers for pose data — no Android binder anywhere, and the client links only liblog, libcutils, libdrm, libutils and libc++.

The consequence is significant: the VR service interface is independent of the Android framework ABI. It would function on any Linux, it does not break across Android versions, and reimplementing it openly (or teaching Monado to speak it) is a protocol reverse-engineering exercise rather than a framework port. The surface that actually matters — connect, handshake, param get/set, ring buffer, sync clock — is roughly a dozen calls out of the 191.

06 — The hard blocker

Controllers are electromagnetic

The Neo 2 does not track its controllers optically. It uses an electromagnetic system, and that is the one subsystem in this device with no open-source path whatsoever.

The chain runs through four proprietary layers:

StageArtifactNature
Coil drivertop_level_bitmap.binFPGA bitstream in a Winbond W25Q SPI NOR, reached through the /dev/w25q char device
Signal processingsns_ndi_fpga (SLPI)Hexagon DSP driver inside signed SLPI firmware
Transportlibssc.soQMI + protobuf from the sensor core
HALsensors-common-ndifpga.pvr.sostandard Android sensors module, ndi_fpga, six values per sample

Per-unit coil calibration sits in /persist/ndi/ as tx1.eep, tx2.eep and rxcache.eep, alongside BLE MACs, serials and per-controller IMU calibration. Buttons come over BLE; pose comes from the EM field.

Reimplementing this would mean reverse-engineering signed Hexagon DSP code and an FPGA bitstream. That is not a realistic goal. The practical answer is that controller tracking is permanently blob-dependent, and any fully-open build either carries these blobs forward or ships without controllers.

One piece of luck. The bitstream lives in the FPGA's own SPI flash, so it survives an OS replacement. A new OS needs only the runtime read path — SLPI firmware, libssc, and the sensor HAL module — never the programming path. And because that module is an ordinary Android sensors HAL, it is one of the more portable blobs in the device.

The bitstream is not in any shipping firmware. It is absent from all three official OTAs and from the Eye dump; the OTA script only stages a copy that must already exist. The only recovery source is a live read of /dev/w25q from a working unit, or a hardware clip on the flash itself.

The real constraint is VNDK 27. Vendor blobs built for Android 8.1 lose their compatibility guarantee quickly, and Google removed the VNDK snapshot mechanism entirely in Android 15. Any route that keeps the stock vendor partition realistically tops out around Android 11, and 9 or 10 will be far less painful. Reaching a genuinely modern Android requires the fully-open route. These two goals are coupled, and that is the central trade in this project.

08 — Sequence

Suggested order of work

Each phase is independently useful and ends in something demonstrable. The gates matter: phase 3 is where the project either becomes a real open platform or settles into a good blob-reuse ROM.

1

Boot a GSI on stock vendor

days · low risk
  • Flash an arm64 A-only Treble GSI, leaving vendor and firmware untouched
  • Disable AVB via vbmeta; keep xbl/abl read-only to avoid the anti-rollback trap
  • Success looks like a display and adb, not a working headset
2

LineageOS with stock vendor + Pico runtime

weeks · moderate
  • Build a device tree for A7B10 against the stock 4.9.65 kernel
  • Carry the compositor and qvrservice across unchanged; rebuild only pvrservice-equivalent glue
  • Ships as a boot+system zip, so no proprietary redistribution
  • This is the backwards-compatible headset, capped near Android 11
3

Mainline kernel bring-up

months · the gate
  • Port from the postmarketOS sdm845 base; extract panel timings from the stock DTB
  • Get the ov9282 pair enumerating through CAMSS as V4L2 devices
  • If the cameras and panel come up, the open platform is real; if not, phase 2 is the ceiling
4

Open XR stack

months · research
  • Mesa/Turnip for graphics, Monado as the OpenXR runtime
  • Basalt or OpenVINS for SLAM, fed by a converter for device_calibration.xml
  • Eye tracking stays unsupported unless the Tobii blob is carried forward
09 — Distribution

Shipping without redistributing blobs

Because this device is non-A/B with a real separate vendor partition, the installer can simply not touch /vendor or /firmware. You ship boot and system; the device supplies its own proprietary blobs from the stock partitions already on it.

That gives a prebuilt one-click zip with no build step for the end user and no proprietary code in your release. If a blob must be staged, the three official Pico OTA zips are publicly downloadable, so an extraction script can pull from a file the user fetches themselves rather than from your server.

10 — Open questions

Not yet established

  • Kernel source. No Pico GPL release located, but this now matters far less than it did: the tree is Qualcomm's reference, so the CAF msm-4.9 baseline (tag family LA.UM.7.1.r1-*-sdm845.0) plus the enumerated Pico overlay fragments should reconstruct it.
  • Which DTBO the device selects at boot. Forty candidates are present and the board-id match hasn't been traced yet; the QVR and SVR entries are the likely ones.
  • QVR wire protocol. The transport is known (Unix sockets + shared-memory ring buffers) but the packet format itself still needs reversing before anything can speak it.
  • Eye-variant vendor partition. Analysis so far used the standard Neo 2 OTA; the Eye's own vendor and oem still need diffing once the backup drive is reconnected.
  • Fastboot state. Unlock status and whether fastboot boot works are unverified on the physical unit.
