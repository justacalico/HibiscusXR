## Deliberately NOT included

- **`libPvr_UnitySDKExt11.so` x28 patch.** Same fix as VRShell's, and the see-through
  app needs it, but the code cave the generic patcher chose landed inside
  `PVR::BufferedFile::~BufferedFile` and hung VRShell (60 threads â†’ 23). Needs a
  cave verified to be genuine dead space between functions, the way the VRShell
  one was.
- **CVService ABI correction.** Lives in `/data/system/packages.xml`, not `/system`.
  PackageManager cached `arm64-v8a` because it first scanned CVService before
  `lib/arm` was restored. On a fresh flash it scans with the libs present and
  derives `armeabi-v7a` itself.
- **8.1 `libtinyxml2.so` / `libicuuc.so` / `libicui18n.so`.** Shadowing these breaks
  Q components in the same process (`libvintf` needs the newer tinyxml2 ctor;
  `libandroidicu` needs ICU 63). Handled by forwarding/stubbing instead.

# The DSP tracking stack (root cause of the black screen)

This is the single most important finding of the port. All of it is proprietary
Qualcomm/Pico content extracted from a stock Pico Neo 2 (PUI 4.1.3) or copied from
the device's own untouched `/vendor` partition.

## Why it matters

Android 8.1 let `/system` processes load libraries from `/vendor/lib`. Android 10's
Treble namespace separation does not, and the LineageOS GSI never carried the
DSP-side files at all. The result was a chain that ended in a black display:

```
libcdsprpc.so missing from /system
  -> libqvr_cdsp_driver_stub.so cannot dlopen it
  -> QVRServiceDspWrapper "UNRECOVERABLE"
  -> QVRServiceTracker: tracker module init failed
  -> "QVRService started. VR mode is not supported."
  -> QVRServiceClient_Create returns NULL
  -> supportedTrackingModes = 0
  -> pose fails the compositor's unit-quaternion check
  -> SelectRT "Bad Pose.Orientation" -> "Nothing to draw, draw black!"
```

Qualcomm's own `/vendor/bin/qvrservicetest64` is the fastest way to check this:
stock prints `starting VR mode`, a broken system prints `VR not supported`.

The version string comes back **from the DSP itself**, which proves FastRPC is
working end to end.

## The QVR client libraries - what actually fixed tracking

The `trackingstate = 0x0,0x0` problem is **solved**. The earlier note that
"neither pvrservice nor VRShell maps any libqvr* library" was the symptom, not a
dead end: the reason pvrservice mapped no `libqvr*` is that it could not.

| File | Source | Installed to |
|---|---|---|
| `libqvrservice_client.so` | `/vendor/lib64`, `/vendor/lib` | `/system/lib64`, `/system/lib` |
| `libqvrcamera_client.so` | `/vendor/lib64`, `/vendor/lib` | `/system/lib64`, `/system/lib` |

Same Treble trap as `libcdsprpc.so`: these ship **only** under `/vendor/lib*`.
`pvrservice` runs from `/system/bin`, and Android 10's namespace separation forbids
a `/system` process loading from `/vendor/lib`. Android 8.1 permitted exactly that,
which is why stock works and we did not.

The failure was silent the whole way down:

```
dlopen("libqvrservice_client.so") fails
  -> QVRServiceClient_Create() returns NULL
  -> svr: "QVR Serivce reported VR not supported"     (sic, vendor's typo)
  -> pvrservice never starts 6DoF
  -> _trackingDataExt +0x9c stays 0
  -> SDK's cached trackingstate stays 0x0,0x0
  -> BoundarySystem::CalculateDialogState -> kLostDialog
  -> compositor rejects every pose, everything black
```

With both libraries in `/system`, pvrservice logs `QVR Service supports rotational
tracking` / `QVR Service supports positional tracking`, maps
`libqvrservice_client.so` for the first time, and all three failure counters go to
zero: `BadPose=0  kLostDialog=0  trackingstate==0x0 count=0`.

`libqvrcamera_client.so` is included for the same reason - it is what `airservice`
and the see-through app need to open the tracking cameras.

## fancontrol - the fan daemon (hardware risk, not just polish)

| File | Source | Installed to |
|---|---|---|
| `fancontrol` | stock `/system/bin` (25768 bytes) | `/system/bin/fancontrol` |
| init rc | stock `/system/etc/init/fanservice.rc` | `/system/etc/init/pn2-fanservice.rc` |

The GSI ships **no fan control whatsoever**. The hardware is there and works - the
kernel exposes a `gpio-fan` cooling device and an hwmon node - but nothing drives
it, so the fan never spins. Under VR load every thermal zone sat at **80-83 C**.

The `gpio-fan,speed-map` in the device tree gives four discrete steps, not a
continuous PWM:

| cur_state | RPM |
|---|---|
| 0 | 0 |
| 1 | 7600 |
| 2 | 9500 |
| 3 | 11400 |

`fancontrol` is small and self-contained: it reads `/sys/class/thermal/thermal_zone1..10/temp`
and drives `/sys/class/hwmon/hwmon1/pwm1_enable` and `pwm1`, with a config path at
`/data/picovr/fan` and logging gated on `persist.pxr.log.fancontrol`. All eight of
its DT_NEEDED libraries (`libbinder`, `liblog`, `libutils`, `libcutils`, `libc++`,
`libc`, `libm`, `libdl`) are already present, so it needs nothing else.

Its init rc needs an explicit `seclabel u:r:shell:s0`. Stock's does not, because
stock's policy defines a `fancontrol` domain (`fancontrol_exec`); ours has no
vendor sepolicy loaded, and init refuses a service with no label it can resolve.

Verified: running as a single instance, the fan holds `cur_state=1` / 7600 rpm with
the hottest zone at ~62 C, matching stock's idle state exactly (`cur=1`, `pwm1=85`,
7600 rpm).

**This one is replaceable without a blob.** The sysfs interface is plain and
writable - `echo 3 > /sys/class/thermal/cooling_device*/cur_state` visibly spins the
fan - so a short shell or C governor can do the same job. A draft is kept at
`overlay/bin/pn2-fand`. The vendor daemon is used for now only because it matches
stock's thresholds exactly; nothing about the hardware requires it.

Stock also runs `thermalserviced` (`/system/bin`, 32608 bytes) which our build lacks,
and ships `com.picovr.factorytest`, which exposes fan RPM among other hardware tests.
Neither is currently installed here.

## Still open: PvrManagerService

VRShell now runs its full native stack (62 threads, correct hmdInfo, no crash) but
stops at its 2D loading screen. It logs:

```
LoadingUtils: start  setting vrmode 2d and ORIENTATION 0
PvrManagerInternal: PvrManagerService dont instantiate properly,please check it.
PVRShell: VirtualDisplay is null
```

and never calls `pvr_EnterVrMode`. The monoscopic "Loading..." is not a rendering
fault - the shell puts itself in 2D deliberately and only switches to stereo once
loading completes.

Stock publishes a binder service `pvr_manager: [com.pvr.IPvrManagerService]` at
service index 22, i.e. from `system_server`. It is a Pico patch to *their*
framework; we run LineageOS's `system_server`, which has no such service. The
client side is `com.pvr.PvrManager` in `/system/framework/pxr_sdk_api.jar` (present
on both devices) and it gates `setSystemFeatures` and VR mode start/stop
(`SXR_ERROR_VRMODE_NOT_INITIALIZED` / `_NOT_STARTED` / `_NOT_STOPPED`).

So the remaining gap is **framework-level, not native**: the 2D-to-VR mode switch
goes through a Pico system service that has to be reimplemented, or reproduced as a
standalone service registered under the name `pvr_manager`, rather than extracted
from the stock image as a blob. That is good news for the open-source goal - it is
Java against public binder APIs, not another opaque `.so`.

## Still open: the CVService crash cascade

`com.picovr.picovrlib.cvcontroller:RemoteService` (32-bit) SIGSEGVs on a null
`sp<BitTube>&` inside `PvrServiceClient::getPvrService()`, respawns about once a
second, and that loop is what wedges everything else:

```
CVService crashes -> respawns ~1/s
  -> each one registerClient()/binderDied() on pvrservice
  -> pvrservice system()s "am startservice -a pvr.intent.action.vrdisplay
     -p com.pvr.vrdisplay --ei action_type 45" from a binder thread
  -> fork() takes every jemalloc arena lock via __bionic_atfork_run_prepare
     while another binder thread sits in free()
  -> pvrservice deadlocks (six unreaped zombie `am` children)
  -> VRShell blocks forever in BpPvrService::registerClient
```

Disabling the controller package clears all of it, which is how VRShell was got
past the hang. The blob issues transact code `0x3b` and builds a `BitTube` from the
reply **without checking the transact result**, so a failed call against a wedged
service produces the null deref. The libraries are byte-identical to stock and the
ABI selection matches (`armeabi-v7a`, `app_process32` on both), so this is a
robustness bug in the blob exposed by the deadlock, not a missing file.

## Note on SELinux

Stock runs qvrservice in `u:r:qvrd:s0`. Our build cannot: init reports
`setexeccon('u:r:qvrd:s0') failed: Invalid argument`, because the vendor sepolicy
is not loaded - `/vendor/etc/selinux/precompiled_sepolicy` expects plat hash
`f6f5bf2d...` and the GSI provides `14484197...`. We run it as `u:r:shell:s0`
instead. SELinux is permissive, and the DSP came up regardless, so this does not
appear to matter for tracking - but it does mean no vendor domain is available to
any service on this build.
